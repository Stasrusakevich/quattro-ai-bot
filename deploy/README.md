# Размещение Quattro Assistant на VPS

Пакет для администратора и программистов, подготовлен 20.11.2026. Служба использует Python 3.12, Telegram long polling и собственный постоянный каталог данных. Команды ниже выполняются на выбранном VPS после сверки действующих служб и версии кода.

## Сверка перед размещением

1. Определить действующие процессы, которые получают обновления токена `@quattro_ai_assistant_bot`. Проверить назначение упомянутого в документах ERP `quattro-ai.service`. Для выбранного токена назначить один принимающий процесс.
2. Уточнить CPU, RAM, свободное место, Python 3.12, systemd и исходящую связь с Telegram. Для включённого AI проверить доступ к выбранному провайдеру и согласованной модели.
3. Зафиксировать commit, владельца выпуска и путь постоянных данных. Сверить перечень зависимостей с `requirements.txt` выбранного commit.
4. Проверить резервную копию данных прежней версии, если сохраняются рабочие записи. Новое ядро использует `DATA_DIR/assistant.sqlite3`. Старую `quattro_ai.db` сохранить отдельно вместе с её версией схемы. Перенос записей в новое ядро выполняется отдельным проверенным импортом. Восстановление старой базы поверх новых записей требует отдельного решения владельца.
5. Подготовить служебную учётную запись и отдельные каталоги. Установленный бот должен иметь права записи в свой каталог данных.

Пример подготовки от администратора при отсутствии такой учётной записи

```sh
sudo useradd --system --home-dir /var/lib/quattro-assistant --shell /usr/sbin/nologin quattro-assistant
sudo install -d -m 0755 /opt/quattro-assistant/releases
sudo install -d -m 0700 -o quattro-assistant -g quattro-assistant /var/lib/quattro-assistant
sudo install -d -m 0700 /var/backups/quattro-assistant
```

Значения исходных ERP-настроек берутся из фактической серверной конфигурации. Бот получает собственный каталог данных. Для каждого внешнего источника программисты согласуют отдельный API-доступ согласно [инфраструктурному контракту](../docs/INFRASTRUCTURE.md).

## Подготовка версии

Положить проверенный checkout в `/opt/quattro-assistant/releases/<полный-commit>`. В этом каталоге создать `.venv` и установить зависимости.

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Сохранить в передаче `git rev-parse HEAD`, `python --version` и итоговый список установленных зависимостей. Выполнить проверки, указанные в передаче ветки. Установленный код и виртуальное окружение принадлежат администратору. После проверки `/opt/quattro-assistant/current` указывает на этот каталог выпуска.

## Настройки

Администратор создаёт `/etc/quattro-assistant.env` с владельцем root и правами `0600`. Значения берутся из `.env.example` выбранного commit. Основные поля

```dotenv
TELEGRAM_BOT_TOKEN=replace_with_bot_token
ADMIN_USER_ID=replace_with_stas_telegram_id
ALLOWED_USER_IDS=replace_with_comma_separated_employee_ids
ALLOWED_CHAT_IDS=replace_with_comma_separated_group_ids
AI_ENABLED=false
AI_PROVIDER=deepseek
AI_MODEL=deepseek-flash
DEEPSEEK_API_KEY=
OPENAI_API_KEY=
ANTHROPIC_API_KEY=
DATA_DIR=/var/lib/quattro-assistant
```

Значения с `replace_` заменяют реальными настройками. `ALLOWED_USER_IDS` и `ALLOWED_CHAT_IDS` задаются списками числовых ID через запятую. Владелец разрешён независимо от списка сотрудников. Пустой список сотрудников оставляет личный доступ владельцу, а список групп определяет разрешённые рабочие группы.

Для запуска с выключенным AI сохраняют `AI_ENABLED=false`. Если переменной нет, AI также выключен, даже при наличии старых ключей. После отдельного согласования модели и расходов задают `AI_ENABLED=true` и ключ выбранного провайдера. Выбор провайдера и модели описан в [AI_CONNECTOR.md](../docs/AI_CONNECTOR.md). Ветка коннектора не меняет production env и не выкладывается на VPS в рамках этой задачи. У `ADMIN_USER_ID` нужен Telegram ID личного пользователя Стаса. Стас предварительно открывает личный чат с ботом и нажимает «Старт», чтобы бот мог доставлять личные уведомления.

Файл окружения и базы содержат рабочую информацию. Их хранят вне Git и каталога выпуска. Обновление кода использует уже настроенное окружение и постоянный `DATA_DIR`.

## Проверка и установка службы

В репозитории подготовлен [quattro-assistant.service](quattro-assistant.service). Проверить его на целевой версии Linux и сопоставить указанные пути с реальными.

```sh
sudo systemd-analyze verify deploy/quattro-assistant.service
sudo install -m 0644 deploy/quattro-assistant.service /etc/systemd/system/quattro-assistant.service
sudo systemctl daemon-reload
sudo systemctl start quattro-assistant.service
sudo systemctl status quattro-assistant.service
```

Проверка `active` подтверждает состояние процесса. Приёмка включает отдельные действия в Telegram

1. Стас выполняет `/start`, затем проверяет доступные команды текущей версии.
2. Сотрудник отправляет тестовую заметку и задачу. Проверяются сохранение, подтверждение автору и доставка Стасу с правильным авторством.
3. Проверяется повторная обработка одного входящего обновления на тестовых данных. Ожидается одна сохранённая запись.
4. При включённом GPT отправляется явный запрос. Проверяются реальный ответ и понятная реакция на недоступность провайдера.
5. В тестовой группе проверяются команды, обычный текст, упоминания и ответы боту. Для групп бот обрабатывает команды.
6. Выполняется контролируемый перезапуск. Проверяются сохранённые записи и статусы отправки.
7. Сверяются журналы. Ключи, содержимое полной переписки и внутренний GPT-контекст в техническом журнале исключаются.

После успешной приёмки администратор включает запуск вместе с сервером

```sh
sudo systemctl enable quattro-assistant.service
```

При ошибке конфигурации или зависимостей исправляется установленная версия и повторяются затронутые пункты. Журнал для диагностики

```sh
sudo journalctl -u quattro-assistant.service --since today
```

В unit задана пауза перезапуска 75 секунд при лимите 5 стартов за 300 секунд. Такая пауза позволяет повторять запуск после временной недоступности Telegram, сохраняя ограничение частых внешних запусков службы. Успешное восстановление сети и последующий запуск проверяются на целевом Linux. После исправления ошибки, приведшей к состоянию `start-limit-hit`, администратор выполняет `systemctl reset-failed quattro-assistant.service` и запускает службу.

## Разрешение неопределённой доставки

Состояние `uncertain` означает, что Telegram мог принять запрос до потери ответа. Следующие части того же уведомления ожидают разрешения этой записи. Решение принимает администратор после сверки адресата, текста или вложения и фактической истории Telegram.

1. Остановить службу и проверить состояние `inactive`. Утилита изменения дополнительно использует тот же `assistant.lock`, что и бот.

   ```sh
   sudo systemctl stop quattro-assistant.service
   sudo systemctl is-active quattro-assistant.service
   ```

2. Создать резервную копию базы по инструкции ниже. В командном клиенте `sqlite3` прочитать спорные записи. Содержимое `payload_json` содержит рабочие данные и используется для административной сверки.

   ```sh
   sudo -u quattro-assistant sqlite3 -readonly /var/lib/quattro-assistant/assistant.sqlite3 ".mode line" "SELECT id,inbox_id,part,method,state,payload_json,telegram_message_id,error_type FROM assistant_outbox WHERE state='uncertain' ORDER BY id;"
   ```

3. Для выбранной записи сопоставить её `chat_id`, содержимое и время с Telegram. Для ответа с вложением проверить каждую часть отдельно. Номер записи outbox и ID сообщения Telegram имеют разные назначения. При подтверждении доставки требуется ID в модели Bot API данного бота. Идентификатор из личного Telegram-моста может отличаться.

4. Если доставка подтверждена и установлен правильный ID сообщения, записать результат утилитой [resolve_delivery.py](resolve_delivery.py). В примере заменить `17`, `1234`, имя оператора и основание реальными данными.

   ```sh
   sudo -u quattro-assistant /opt/quattro-assistant/current/.venv/bin/python -B /opt/quattro-assistant/current/deploy/resolve_delivery.py /var/lib/quattro-assistant/assistant.sqlite3 17 --expected-state uncertain --operator "admin-name" --reason "Сверено со Стасом в Telegram, доставка подтверждена" --sent-message-id 1234
   ```

5. Если достоверно установлено, что сообщение не отправлено, разрешить повтор выбранной записи.

   ```sh
   sudo -u quattro-assistant /opt/quattro-assistant/current/.venv/bin/python -B /opt/quattro-assistant/current/deploy/resolve_delivery.py /var/lib/quattro-assistant/assistant.sqlite3 17 --expected-state uncertain --operator "admin-name" --reason "История и результат запроса сверены, отправки не было" --confirmed-not-delivered
   ```

6. Если результат остался неопределённым или ID подтверждённой доставки получить нельзя, сохранить `uncertain` и передать вопрос владельцу. Обычный `/retry_notifications` обрабатывает явные ошибки `failed`.

Утилита изменяет только одну существующую запись со статусом `uncertain` и схемой текущей версии. Для подтверждённой доставки устанавливаются `sent` и `telegram_message_id`. Для подтверждённого отсутствия отправки устанавливаются `pending` и `next_attempt=0`. В той же транзакции добавляется запись аудита `manual_delivery` с оператором, основанием и результатом. Ошибочный ID, изменившееся состояние или сбой аудита отменяют всю операцию.

После сверки прочитать состояние выбранной записи и аудит, затем запустить службу. Очередь продолжит разрешённую доставку, сохраняя успешно отправленные части.

```sh
sudo -u quattro-assistant sqlite3 -readonly /var/lib/quattro-assistant/assistant.sqlite3 ".mode line" "SELECT id,state,telegram_message_id FROM assistant_outbox WHERE id=17;" "SELECT action,details,created_at FROM assistant_audit WHERE action='manual_delivery' ORDER BY id DESC LIMIT 5;"
sudo systemctl start quattro-assistant.service
```

## Резервная копия и восстановление

Утилита [backup.py](backup.py) использует штатный SQLite backup API, создаёт новый файл и проверяет `integrity_check`. Путь исходной базы берётся из конфигурации приложения. Пример для явного пути

```sh
sudo python3.12 deploy/backup.py /var/lib/quattro-assistant/assistant.sqlite3 /var/backups/quattro-assistant
```

Путь сверяют с фактическим `DATA_DIR`. Для работающей базы SQLite в режиме WAL резервная копия создаётся через backup API или после согласованной остановки всех писателей с проверкой целостности. Каталог резервных копий должен быть доступен только назначенному администратору.

Администратор назначает периодичность согласно допустимой потере данных, контролирует успешность и свободное место, передаёт копию в отдельное хранилище согласно действующей политике Quattro. Утилита сохраняет все созданные копии. Срок хранения и очистку определяет владелец данных.

Восстановление проверяется в отдельном каталоге с отдельным тестовым токеном или полностью отключённой отправкой. Сначала выполняются `integrity_check` и сверка нескольких записей, затем запуск тестового экземпляра. Для рабочего восстановления фиксируются причина, выбранная копия, время и согласование потери записей после даты копии.

## Обновление и откат

1. Зафиксировать текущий commit и получить согласованную копию базы.
2. Подготовить новый каталог выпуска и его `.venv`, выполнить приёмочные проверки на копии данных.
3. Остановить службу, выбрать новый `current`, запустить её и проверить изменённые сценарии.
4. При ошибке приложения остановить службу, вернуть предыдущий каталог кода и запустить его с текущими данными, если схема обратно совместима.
5. Отдельно проверить сохранённые записи, состояние отправок и единственный процесс приёма обновлений.

Миграции в будущих версиях выполняются последовательно с собственным номером и резервной копией. Разрушающие изменения требуют заранее согласованного плана переноса и отката.

## Передача расписаний и подключений

На рабочем компьютере сейчас есть Codex-расписания контроля продаж и подготовки мероприятий. Приём кода бота на VPS сам по себе не переносит эти задания. Для каждого переноса программисты фиксируют имя задания, расписание в `Europe/Moscow`, источники, назначение сообщений, ключ защиты от повторов и владельца запуска.

До включения серверного таймера требуется проверка, что прежний владелец прекратил выполнять перенесённый этап. Сначала проверяется одно задание с наблюдаемым результатом, затем последовательно переносятся остальные. В передаче фиксируется дата первого успешного серверного запуска.

Google Sheets, ERP и Битрикс24 подключаются через согласованные служебные учётные записи. Наличие пользовательского подключения в Codex подтверждает работу текущего сеанса. Серверному боту требуется собственная проверенная авторизация и журнал результата каждого запроса.

## Состояние проверки этого пакета

20.11.2026 локально на Windows проверены успешная копия SQLite, сохранение исходной базы, уникальность имён повторных копий, очистка незавершённого файла при ошибочной базе и отказ для отсутствующего источника. На отдельной тестовой базе в WAL проверена согласованность копии при одновременной записи транзакций. Выполнена статическая проверка секций службы, пользователя, пути данных и команды запуска.

Для утилиты разрешения доставки выполнены девять проверок на временных базах. Подтверждены запись `sent` с аудитом, разрешённый повтор `pending`, отказ для неверного ID, изменившегося состояния, неверных параметров и неизвестной схемы, атомарный откат при ошибке аудита, блокировка работающим экземпляром и сохранность отсутствующего пути. Команда повторения этих проверок

```sh
.venv/bin/python -B -m unittest deploy.test_resolve_delivery -v
```

Номер commit входит в общую передачу ветки. Systemd unit требует `systemd-analyze verify` на целевом Linux. Права пользователя, действующие процессы, исходящая связь, ресурсы, настоящие ключи, серверная отправка и восстановление на VPS проверяются командой размещения.
