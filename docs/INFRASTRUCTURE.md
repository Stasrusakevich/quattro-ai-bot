# Инфраструктура Quattro Assistant

Решения для передачи программистам от 20.11.2026. Целевая площадка — существующий VPS ERP Quattro. Серверные изменения выполняет команда размещения после проверки ресурсов и действующих служб.

## Подтверждённая основа

В локальной копии ERP `Stasrusakevich/quattrospace`, коммит `07939411eec9643a682b18454a0521ee301625b4`, изучены `docs/VPS_CICD.md`, `deploy/vps/compose.yml`, `server/runtime.ts` и `server/sqlite.ts`. Эта версия содержит Node/VPS-адаптер, SQLite с WAL, `synchronous=FULL` и ожиданием блокировки. Данные ERP находятся в постоянном томе Compose. Фактическую версию, диски, ресурсы и процессы VPS предстоит сверить на сервере.

В документации ERP упомянут `quattro-ai.service`. До включения нового процесса администратор выясняет назначение этой службы и всех обработчиков токена `@quattro_ai_assistant_bot`. Для одного Telegram-токена работает один получатель обновлений. Службу с другим назначением сохраняют под её действующим именем.

## Первый запуск

Достаточны Python 3.12, один процесс бота и собственная SQLite на локальном постоянном диске. Telegram обслуживается через long polling. Публичный входящий порт для этого режима отсутствует. Исходящие подключения нужны к Telegram и, при включении GPT, к OpenAI. DNS и системное время должны работать.

Существующий подход ERP к постоянным данным совместим с такой организацией. Для запуска бота отдельные Redis, брокер очередей и сервер PostgreSQL не требуются. Решение о расширении принимают по наблюдаемой нагрузке и ограничениям, когда появятся несколько независимых писателей или длительные фоновые операции.

| Область | Размещение и владелец |
| --- | --- |
| Код конкретной версии | `/opt/quattro-assistant/releases/<commit>` под управлением администратора |
| Текущий выпуск | `/opt/quattro-assistant/current`, ссылка на выбранную версию |
| Исполнение | Пользователь и группа `quattro-assistant` |
| Настройки и ключи | `/etc/quattro-assistant.env`, права `0600`, владелец root |
| Рабочие данные | `/var/lib/quattro-assistant/assistant.sqlite3`, каталог с правами `0700`, владелец службы |
| Журнал процесса | journald с действующей ротацией и контролем места |
| Копии базы | Каталог вне каталога выпуска, отдельное хранение согласно политике владельца |

Сервис бота получает запись в свой каталог данных. Бизнес-базы ERP, ключи выпуска и рабочие секреты других служб остаются у своих владельцев. Подключение бота к ERP организуется через согласованный служебный API и ограниченную учётную запись. Прямое подключение к SQLite ERP обходит её проверки, версии и аудит, поэтому в контракт интеграции входит API.

## Контракты перед включением интеграций

### Мероприятие и версия источника

Ключом мероприятия служит стабильный `event_id` ERP. Дата, зал и название помогают сопоставлению и отображению. Изменение даты или названия сохраняет связь того же мероприятия. Для нескольких залов передаётся общий ключ мероприятия и отдельные ключи броней.

Минимальная запись адаптера содержит `source`, `event_id`, `booking_ids`, `source_version`, `read_at`, `event_date`, `timezone`, `venue`, `halls`, `manager_id`, `executor_id`, `estimate_id`, `estimate_version`, `approval_state` и ссылки на источники. Поля с отсутствующим подтверждением имеют явное состояние `unknown` или `unconfirmed`.

Адаптер чтения возвращает данные и фактическую версию. Адаптер изменения принимает ожидаемую версию. Если версия изменилась, операция возвращает конфликт и новые данные для сверки. Автоматическое затирание более свежего изменения исключается.

Часы смены хранятся с полной датой начала, датой окончания и зоной `Europe/Moscow`. Это позволяет корректно учитывать смену до 01:00 следующего дня и многодневные мероприятия. Оплаченное время в смете и согласованный фактический план выхода доступны как разные значения.

### Будущий адаптер изменений ERP из Telegram

Дополнение от 23.11.2026 предусматривает расширение чтения ERP на запись
по поручению менеджера. Чтение и изменение имеют отдельные обработчики;
до реализации и приёмки сценария изменения не выполняются.
Рассматриваемый упрощённый вход с действующим паролем ERP относится к первому
подключению чтения. Возможность прочитать все нужные поля ещё проверяется.
Такой вход не заменяет проверку полномочий автора будущих изменений.

Предложение изменения содержит `operation_id`, исходное сообщение и Telegram ID
автора, `event_id`, затронутые `booking_ids`, ожидаемую версию ERP, явное действие
«добавить/установить/удалить», разрешённые поля и значения до/после.
Подтверждение привязывается к автору, конкретному предложению и версии.
ERP проверяет права, занятость, связанные залы и бизнес-правила штатной операции
сохранения. Прямое редактирование SQLite для этого сценария не применяется.

Ключ операции должен предотвращать повторную запись и после перезапуска бота.
При таймауте после отправки изменения адаптер выясняет результат по ключу
операции/аудиту, прежде чем повторить запрос. При отсутствии такого контракта
неопределённую запись оставляют для сверки. Новая версия согласованной сметы
связывается со сверкой задач, чек-листа и плана табеля; сбой каждого следующего
шага сохраняет отдельный статус и допускает продолжение без повторной правки ERP.

Приёмка будущего модуля должна включать: неоднозначную бронь и пустые поля;
добавление количества против замены итогового количества; отмену предпросмотра;
чужую бронь и неподтверждённый ID; успешную правку и повторное чтение;
одновременную правку из ERP; занятой зал; повтор подтверждения и перезапуск;
потерянный ответ после записи; сохранность имён и факта в табеле;
частичный сбой синхронизации документов. Эти сценарии пока не реализованы
и не проверены. Порядок подтверждения и разрешённые поля описаны
в [рабочих правилах](BOT_INSTRUCTIONS.md#будущий-этап-изменение-брони-по-сообщению-менеджера).

### Задачи и отправка

Для входящего сообщения ключ повтора — Telegram `update_id` и, где применимо, пара `chat_id/message_id`. Для задачи ключ включает мероприятие, позицию сметы и тип операции. Изменение согласованного состава хранит новую версию задачи и связь с прежней записью.

Запись намерения отправить сообщение создаётся в одной транзакции с изменением бизнес-состояния. В outbox сохраняются `operation_id`, `dedupe_key`, версия источника, адресат, тема или обсуждение, состояние, число попыток, следующий допустимый повтор и идентификатор результата Telegram.

| Результат внешней операции | Дальнейшее действие |
| --- | --- |
| Получен успешный ответ с ID сообщения | Зафиксировать результат и завершить операцию |
| Явная временная ошибка до подтверждённой доставки | Повторить с ограничением и учётом `retry_after` |
| Запрос мог выполниться, но ответ потерян | Пометить результат как неопределённый и сверить историю или запросить проверку |
| Источник недоступен либо недостаточно прав | Сохранить задание и показать, какая часть проверки не выполнена |

У Telegram нет общего клиентского ключа идемпотентности для `sendMessage`. При потере ответа обещание строго однократной отправки требует сверки, поэтому неопределённые запросы не повторяются вслепую. При восстановлении процесса записи, которые находились в отправке, проходят такую же сверку.

Для форумной группы сохраняются `chat_id`, `message_thread_id` и ID ответа в модели Bot API. У обычной группы ID сообщения, увиденный через личный Telegram-аккаунт, может отличаться от ID Bot API. Адаптер проверяет соответствие перед формированием ответа.

### План и факт персонала

Одна плановая строка соответствует одному сотруднику на конкретной роли и смене. Для неё выделяются стабильные `personnel_slot_id`, `event_id`, `estimate_line_id`, `plan_version`, исходные плановые часы, актуальные плановые часы, имя, фактические часы, отметка реализатора и флаг проверки.

Количество увеличивается добавлением новых слотов с собственными ID. Сокращение плана переводит лишние незаполненные слоты в отменённое состояние. Заполненный слот сохраняется и получает отметку проверки реализатором. Изменение плана обновляет плановые поля и сохраняет уже внесённые имя и факт. Первоначальный план остаётся в истории версий. Факт подтверждается явной отметкой реализатора с автором и временем.

Транзакция сверки принимает версию табеля. Одновременное внесение факта реализатором и изменение плана менеджером вызывает конфликт или безопасное слияние независимых полей. Операция из устаревшей копии не может молча заменить внесённый факт.

### База знаний Quattro

Для материала нужны `knowledge_item_id`, заголовок, раздел, источник или ссылка, владелец, редакция, дата действия, доступные роли и статус утверждения. Черновики и устаревшие записи сохраняют свой статус. Ответ GPT получает только доступные пользователю утверждённые материалы и сообщает источник, когда опирается на внутреннее правило.

Сообщение сотрудника сначала сохраняется как предложение или заметка. Включение его в утверждённую базу знаний выполняет ответственный редактор. Полученные из документов инструкции об отправке, изменении прав или удалении данных рассматриваются как содержимое источника. Бизнес-действия исполняются через проверенный сценарий и права пользователя.

Поиск первых версий может работать по тексту и разделам. Выбор отдельного поискового или векторного сервиса обосновывается объёмом материалов и проверкой качества поиска. Финансовые данные и личные заметки не становятся общедоступной базой знаний автоматически.

## Роли, аудит и финансовые данные

В первой версии `ADMIN_USER_ID` определяет владельца, `ALLOWED_USER_IDS` содержит подтверждённые Telegram ID сотрудников, `ALLOWED_CHAT_IDS` содержит согласованные рабочие группы. Владелец имеет доступ независимо от списка сотрудников. Имя и username используются для отображения. Расширение на роли ниже требует отдельной реализации и проверки. Общий чат и членство в группе сами по себе не дают финансовые права.

| Роль | Предполагаемая область полномочий |
| --- | --- |
| Стас / владелец | Личные задачи и заметки, согласованные сводки и финансовый контроль |
| Менеджер | Свои мероприятия, сметы, чек-листы и подтверждение расхождений |
| Реализатор | Организация заказов, назначение исполнителей, имена и факт смен |
| РОП | Утверждённые сделки, показатели и отчёты команды продаж |
| Редактор знаний | Утверждение материалов своей области |
| Администратор сервиса | Эксплуатация, технические журналы и восстановление |

Фактическую матрицу доступа утверждает Стас перед включением соответствующего модуля. Для финансового контроля отдельно определить получателей каждой сводки и уровень детализации. Финансовые расхождения содержат источники, даты и состояние подтверждения. Автоматическая отправка показателей в рабочую группу требует согласованного назначения этой группы.

Аудит хранит время UTC, идентификатор операции, пользователя, действие, сущность, версии до и после, адресата внешнего действия и результат. Журнал процесса содержит технический статус и ID операции. Секреты, полная клиентская переписка и полный контекст GPT в технические журналы не попадают.

## Фоновые проверки и единственный владелец расписания

Сейчас в Codex на рабочем компьютере действует вечерняя проверка в 19:00 по Москве. Она проверяет завтрашние мероприятия и наличие чек-листов в ближайшие три дня. Отдельное расписание РОП действует в 10:00, 19:00 и 21:00. При переносе на VPS для каждого задания определяют одного владельца запуска и одного владельца доставки.

В записи задания требуются имя, версия правил, дата проверки, слот, статус, начало, окончание, свежесть источников и результат отправки. Ключ `(job_name, business_date, slot)` защищает от повторной публикации того же этапа. Таймер может запускать обработчик повторно, а обработчик сначала проверяет состояние задания и результаты прежнего запуска.

При позднем запуске определяются фактическая московская дата и актуальные мероприятия. Для нового запуска читаются свежие источники. После переноса расписания прежний владелец должен прекратить выполнение именно перенесённых заданий, что подтверждается отдельной сверкой.

## Проверки перед расширением

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Два сотрудника одновременно отправили заметки | Обе сохранены с собственными авторами и ID |
| Повтор Telegram update после перезапуска | Одна бизнес-запись и понятное состояние доставки |
| Ошибка GPT | Входящие заметки продолжают сохраняться |
| Потеря ответа Telegram после отправки | Операция помечена для сверки, слепого повтора нет |
| Изменение сметы одновременно с заполнением факта | Имя и фактические часы сохранены, конфликт показан |
| Новая версия сметы уменьшила количество персонала | Лишние слоты отражены в истории, заполненные отмечены для проверки |
| Пользователь запросил чужую финансовую информацию | Проверена роль и область доступа, результат соответствует матрице |
| Материал знаний изменён редактором | Видны актуальная редакция, источник и дата действия |
| Два владельца расписания запускают один слот | Доставка подтверждается одним владельцем и одним ключом этапа |
| Восстановление из копии в отдельный каталог | Проверены целостность, актуальность и сохранность рабочих записей |

## Что необходимо получить от команды VPS

1. Фактический сервер, Linux/systemd, версия Python, свободные CPU, RAM и диск, работающие процессы бота и назначение `quattro-ai.service`.
2. Выбранный commit ветки, способ сборки, владелец выпуска, постоянный каталог данных, резервные копии и место для проверки восстановления.
3. Токен Telegram, личный `ADMIN_USER_ID`, права бота в целевых чатах. Ключи передаются по действующему защищённому каналу команды.
4. Для GPT — доступная модель, рабочий API key, плательщик и согласованный лимит расходов.
5. Для ERP — API-контракт, тип служебной авторизации, стабильные ID, версии и область разрешённых операций.
6. Для Google — служебная авторизация с доступом только к согласованным таблицам. Пользовательский коннектор Codex подтверждает доступ текущего сеанса и требует отдельного решения для серверного процесса.
7. Для Битрикс24 и финансов — сущности, поля, права и порядок подтверждения исходных данных.
8. Для базы знаний — действующие материалы, владельцы разделов и порядок публикации редакций.

Точная процедура первого размещения и проверки находится в [deploy/README.md](../deploy/README.md).
