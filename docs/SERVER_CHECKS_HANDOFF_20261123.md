включающий объединённый PR № 2. Полное согласованное ТЗ находится в

## Подготовлено в этой ветке

`integrations/erp.py` читает действующие запросы ERP через существующий парольный
вход. По форме определяется общий либо персональный вход. При персональном
входе нужен логин уже существующего пользователя. Cookie находится в памяти
процесса. После 401 допускается один повторный вход. Неверный пароль прекращает
дальнейшие попытки в этом клиенте. GET повторяется максимум один раз при
транспортном сбое или 502/503/504. POST входа автоматически не повторяется.
429 останавливает обращения на срок Retry-After.

Чтение ограничено выбранным периодом до 31 дня. Сначала читается компактный
календарь, затем карточки только найденных мероприятий. Запросы последовательны,
число мероприятий ограничено 100. Превышение лимита даёт неполный результат.
Смета читается целиком, включая состав и статус. Залы, гримёрная, многодневные
брони, отмены, предброни и монтаж/демонтаж сохраняются в исходном виде.
Старые записи без projectId выделяются отдельно и требуют сверки.
Активная старая бронь без связи с мероприятием делает итог неполным.
Техническая блокировка и отменённая запись без projectId сохраняются в снимке.

Чтобы обнаружить параллельную правку, читается группа броней, карточка и снова
группа. Сверяются версия карточки и версия группы. При изменении допускается
одна новая попытка. После всего периода проверяется его viewToken. При изменении
календаря отчёт считается неполным. Получение отчёта не блокирует последующие
изменения менеджеров, поэтому это снимок на указанный момент чтения.

`python -m checks.preview` выполняет отдельное пробное чтение. Оно сохраняет
частный JSON в `DATA_DIR/checks`, включая проверенные части при сбое. Файл
создаётся с правами 0600 на Linux. Вывод в консоль содержит путь и общие статусы.
Состав сметы, контакты, пароль и cookie в консоль не выводятся. `data/` исключён
из Git. Снимки содержат рабочие данные, при проверке нужно использовать тестовые
мероприятия и ограничить доступ к каталогу.

В JSON присутствуют `erp_complete` и отдельный `readiness_checked=false`.
Успешное чтение ERP ещё не оценивает готовность мероприятия. Источники
Google-чек-листов и переписки отмечены как `not_connected`.

## Что требуется от программистов и администратора

1. Проверить ветку и контракт на действующей версии ERP. В серверном окружении
   добавить `ERP_BASE_URL`, `ERP_PASSWORD`, имя общего входа `ERP_LOGIN_NAME`.
   `ERP_USERNAME` нужен только для уже включённого персонального режима.
   Использовать выбранный Стасом существующий вход. Пароль передать через
   серверные секреты, в чат и Git его не помещать. У общего входа остаются
   широкие права, ограничение чтения обеспечивает текущий адаптер.
2. Запустить пробное чтение тестового мероприятия на VPS. Подтвердить доступность
   `/api/calendar/view`, `/api/projects/{id}` и `/api/projects/{id}/reservations`,
   наличие полного состава сметы, `projectRevisions`, `reservationGroupRevisions`,
   статуса сметы и связей всех залов. Если контракт расходится, передать точное
   различие без клиентских данных и секретов. Дополнительный API согласовать
   только при конкретном пробеле в существующих ответах.
3. Настроить серверный доступ Google к двум документам из полного ТЗ и реализовать
   адаптер Sheets с обновлением авторизации. Сначала читать метаданные, затем
   нужные вкладки и диапазоны. Коннекторы Codex не предоставляют VPS свои права.
   В первом этапе операции Google выполняются только для чтения.
4. Реализовать сопоставление ЧЛ по мероприятию, датам, залам, клиенту и менеджеру.
   Шаблон gid 1081802822 исключается. Копии, конечные пробелы, многодневность и
   частичные ЧЛ обрабатываются явно. При неоднозначности нужен статус уточнения.
5. Реализовать проверку завтра и независимый контроль ЧЛ на следующие три дня.
   Учитывать все роли и примечания, вызов/подтверждение персонала, смены,
   реализатора, тайминг, технику и особые условия. Пустая отметка вызова означает
   вопрос о подтверждении. Расхождение со сметой предъявляется менеджеру.
6. Добавить приём доступных новых сообщений разрешённых рабочих групп и
   подтверждённое сопоставление Telegram ID с ERP-пользователем. Существующий
   обработчик групп принимает команды, произвольный анализ переписки ещё
   предстоит реализовать. Не запускать второй polling-процесс того же токена.
   Настроить события/режим доступа Bot API и хранение обсуждений по мероприятию.
7. Добавить постоянный журнал заданий, уникальный ключ запуска, хранение
   нерешённых вопросов и транзакционную очередь исходящих сообщений. Использовать
   логику существующей outbox там, где она подходит. Входящие ответы, повторный
   запуск и рестарт не должны создавать повторные напоминания. Неопределённая
   доставка требует сверки. 429 обрабатывается по retry_after.
8. Подключить согласованные адресаты из полного ТЗ. Общие вопросы идут в чат
   реализации, напоминания об отсутствии ЧЛ — в рабочую группу, тема 688.
   Готовность, отсутствие мероприятий и сбои источников сообщаются владельцу
   согласно ТЗ. Автоматические кейтеринговые рассылки ещё не определены.
9. Настроить 19:00 Europe/Moscow на существующем VPS. Сначала тестовый прогон,
   затем сверка результата. Переключение владельца расписания с automation-3
   выполнить согласованно, после этого подтвердить единственного исполнителя.
   До переключения сохраняется текущая автоматизация Codex.
10. Проверить разрешённого сотрудника, команды из согласованных групп, запрет
    неизвестного пользователя, рестарт службы и восстановление резервной копии.
    Серверный каталог бота и служба ERP должны оставаться работоспособны.

Финансовый контроль, табель, Битрикс/РОП и запись в ERP остаются следующими
этапами по полному ТЗ. Отмена брони и отметки об оплате требуют отдельных прав.
Существующие правила ERP допускают пересечения броней с предупреждением.

## Пробный запуск на VPS

После настройки переменных окружения и установки зависимостей выбранной ветки
запустить из её каталога под служебным пользователем бота

```sh
.venv/bin/python -B -m checks.preview --from 2026-11-24 --to 2026-11-27
```

Конец периода исключается. Без параметров читаются три дня начиная с завтра
по Москве. Команда загружает `.env`, если такой файл существует, и принимает
серверное окружение. Существующие переменные окружения имеют приоритет.
Код завершения 0 означает полное пробное чтение ERP. Код 2 означает ошибку
либо неполный снимок. Передача ЧЛ, готовность и доставка этим кодом не подтверждены.
Сначала использовать период с тестовым мероприятием, выбранный администратором.

## Проверки и приёмка

| Требование и состояния | Реализация | Проверка и текущая граница |
| --- | --- | --- |
| Общий и персональный вход, cookie, 401, неверный пароль | ERPClient | Тесты на подменённых HTTP-ответах, живой вход на VPS предстоит |
| 429, сеть, 503, ограниченные повторы, редиректы | ERPClient | Локальные сценарии ошибок, реальные сетевые условия предстоят |
| Отдельная смета со связанными залами и днями | event, collect | Тестовый состав сметы и группа, рабочие данные ещё не проверены |
| Отмена, техническая блокировка, гримёрная и старая запись | collect | Сохранение исходных строк в локальном отчёте, без оценки готовности |
| Одновременная правка, неполный ответ и смена периода | event, collect | Версии карточки/группы и токен периода проверены локально |
| Пустой календарь против недоступной ERP | collect | Разные статусы и коды завершения проверены локально |
| Частный отчёт и исключение секретов | write_report, ERPSettings | Запись/чтение тестового файла и отсутствие пароля в repr |
| Google, матч ЧЛ, персонал, ответы команды | Пункты 3–6 выше | Предстоит реализовать и проверить |
| 19:00, три дня, журнал/очередь, Telegram и защита повторов | Пункты 5–9 выше | Предстоит реализовать и проверить |
| Рестарт VPS, восстановление и независимость от ПК | Пункты 9–10 выше | Живая приёмка обязательна |

Локальные команды проверки

```sh
.venv/bin/python -B -m unittest discover -s tests -v
.venv/bin/python -B -m unittest discover -s deploy -p 'test_*.py' -v
.venv/bin/python -m pip check
git diff --check
```

В Windows используется `.venv/Scripts/python.exe`. Тесты ERP используют
`httpx.MockTransport`, временные файлы и синтетические сметы. Новых сообщений
Telegram и обращений к рабочей базе эти тесты не выполняют.

23.11.2026 в Windows/Python 3.12 прошли 57 тестов приложения и 9 тестов
инструментов эксплуатации. Из них 34 проверяют новый модуль. Также прошли
`pip check`, справка команды preview и `git diff --check`. Живой вход ERP,
реальное чтение смет на VPS и Google/Telegram этим результатом не подтверждены.

Ветка предназначена для review и дальнейшего подключения. Слияние в main
запускает автодеплой и требует отдельной команды Стаса на конкретный выпуск.
