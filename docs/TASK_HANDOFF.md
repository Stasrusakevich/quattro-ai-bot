## Поручение

Подготовить с нуля чистую основу бота и рабочие инструкции в GitHub.
Программисты размещают его на существующем VPS ERP. В ходе подготовки выполнены
локальные проверки на синтетических данных. Изменения рабочих серверов
и запуск обработчика с рабочим Telegram-токеном относятся к приёмке команды VPS.

Прежние конкурирующие обработчики pyTelegramBotAPI и python-telegram-bot,
многошаговые формы ОС, режимы продаж и старые экспорты удалены из активного кода
в соответствии с решением начать бота с нуля. Существующие рабочие записи
сохраняются в отдельной прежней базе до согласованного импорта. Исторические
материалы базы знаний сохранены для проверки редактором.

## Среда и проверки

Локальная среда Windows, Python 3.12.14, python-telegram-bot 21.6,
python-dotenv 1.2.4, openai 2.54.0. Команда проверки

```sh
.venv/bin/python -B -m unittest discover -s tests -v
.venv/bin/python -B -m unittest discover -s deploy -p 'test_*.py' -v
```

На Windows используется `.venv/Scripts/python.exe`. Тесты создают временные базы,
подменяют Telegram/OpenAI и проверяют обработку через стандартный вход
`Application.process_update`. Первый запуск async-тестов был заблокирован
ограничением внутреннего socketpair Windows. Повтор выполнен с разрешённым
локальным каналом, сохранив подмену внешних сервисов.

В итоговом прогоне ядра прошли 23 теста, включая удержанный медленный ответ GPT
с параллельным сохранением заметки другого пользователя и доставку вложения
по сохранённому file_id. Ещё 9 тестов подтвердили ручное разрешение неопределённой
доставки, общий lock, аудит и откат всей операции при ошибке. Всего 32 теста.
Также прошли разбор синтаксиса Python, `pip check`,
`git diff --check`, проверка локальных ссылок документации и проверка состава
публикуемых файлов на ключи и базы. Файлы данных и рабочие ключи исключены
из публикуемого набора.

Резервная копия проверена отдельным техническим проходом на обычной SQLite,
при конкурентной записи в WAL, отсутствии источника, ошибке целостности
и повторном вызове. Статическая структура systemd unit проверена. Linux и
`systemd-analyze` в этой среде отсутствуют.

## Приёмка программистами

1. Инвентаризировать фактический VPS и существующий `quattro-ai.service`,
   выбрать одного получателя обновлений рабочего токена.
2. Подготовить env, постоянный каталог и резервную копию согласно deploy/README.md.
3. Указать IDs владельца, сотрудников и разрешённых групп. Владелец открывает
   личный чат с ботом. Проверить реальную доставку заметки и задачи.
4. Подключить согласованную модель OpenAI и проверить живой ответ и ошибку API.
5. Выполнить серверную приёмку, перезапуск и восстановление из копии.
6. Согласовать служебные API ERP, Google и Битрикс24, затем реализовать рабочие
   модули по переданным требованиям и включать их с отдельной приёмкой.
7. Передавать расписания с одним владельцем запуска и подтверждением первой
   серверной доставки, учитывая текущие задания Codex.

Запуск ядра не подтверждает готовность интеграций, описанных в таблице требований.

## Мультипровайдерный AI-коннектор, 25.11.2026

Ветка `feat/multi-provider-ai-connector` создана от `origin/main` на базе
`ada8613`. Checkout клонирован в локальную папку `projects/quattro-ai-bot`,
поскольку существующая копия этого репозитория там не обнаружена.

Добавлены DeepSeek Chat Completions и Anthropic Messages; OpenAI сохраняет
Responses API с `store=False`. Общий вход `generate_ai_response` передаёт
всем адаптерам прежние инструкции, справку и допустимую историю. Выбор через
`AI_PROVIDER` и `AI_MODEL`, отдельный ключ каждого провайдера. Нет fallback
и автоматических повторов. По умолчанию `AI_ENABLED=false`; даже старый env
с ключом OpenAI без нового флага оставляет AI выключенным. DeepSeek по
умолчанию использует официальный API ID `deepseek-flash`.

Подробности, источники API, примеры env и ограничения находятся в
[AI_CONNECTOR.md](AI_CONNECTOR.md). `/gpt`, `/ask` и меню сохранены.
`/status` владельца учитывает выбранного провайдера и выключенный режим.

Локальная проверка: macOS, Python 3.13.3, зависимости из `requirements.txt`.
41 тест бота/коннектора и 9 тестов разрешения доставки (всего 50). Новые
проверки используют реальную сериализацию OpenAI SDK и HTTPX MockTransport,
тестовый dotenv и временную SQLite. Дополнительно проверены зависимости
(`pip check`), синтаксис Python 3.12 через `ast.parse(feature_version=(3, 12))`,
локальные ссылки и `git diff --check`.

Живые API AI и Telegram не вызывались; модель и биллинг на реальных аккаунтах
не проверены. Python 3.12 локально отсутствует: выполнение на нём отдельно
не проверено. Существующая CI-конфигурация с Python 3.12 оставлена без изменений.
Базы, системные инструкции, справка, алгоритм доступа, очередь доставки и
systemd unit не изменены. Production env и секреты не читались и не менялись.
Деплоя на VPS и merge в main в этой задаче нет; передаётся отдельная ветка.
